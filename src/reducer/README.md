# reducer

Baseline ddmin и dependency-aware вариант; владелец Aldiyar.

Реализовано (Go, 14 ноября 2026): `src/reducer` — классический ddmin (Zeller) на множестве ID вмешательств, последовательное удаление (baseline), dependency-aware вариант (та же логика ddmin, кандидаты упорядочены по `LeafFirstOrder`, см. ADR-005: только порядок, не критерий принятия). Общий бюджет (запуски + секунды), подтверждение принятого кандидата 3/3, пометка `unstable` при флуктуации. Модуль не зависит от Docker/HTTP/Postgres — алгоритмы покрыты unit-тестами с фейковым Executor (`src/reducer/reducer_test.go`) и отдельно проверены на реальном стенде через `POST /api/runs/{id}/reduce` (см. tests/integration).

Обновление 18 ноября 2026 (DEMO-52, результаты: VERIFICATION.md):

- Исходный полный набор подтверждается 3/3 (1 пробный + 3 подтверждающих запуска) до любого сокращения. Каждый принятый кандидат подтверждается 3/3; кандидат, воспроизведённый один раз, но не 3/3, отклоняется с пометкой Unstable; всегда отдаётся последний подтверждённый набор.
- Бюджет (NFR06) списывается за каждое исполнение, включая подтверждения и проверку пустого набора; попадания в кэш результатов бесплатны (`CacheHits`). `Budget.Clamp` ограничивает 100 запусками / 10 минутами; первая достигнутая граница даёт `BUDGET_EXHAUSTED_RUNS` или `BUDGET_EXHAUSTED_SECONDS` (исполнение, прерванное дедлайном, — бюджетная остановка, не infra-ошибка). При infra-ошибке и отмене возвращается частичный результат (`INFRA_ERROR` / `CANCELLED`).
- Перед признанием результата минимальным проверяется пустой набор. `OneMinimal` означает 1-minimal относительно допустимых кандидатов и проверенных условий, не глобальный минимум.
- Допустимость кандидатов по `depends_on` сценария (`Options.Valid`) одинакова для ddmin, sequential и dependency_aware; у dependency_aware отличается только порядок (`LeafFirstOrder`). `Options.Valid` к полному набору не применяется. `sequential` повторяет проходы до неподвижной точки.
- Тесты: 33 юнит-теста верхнего уровня (`reducer_test.go` 6, `acceptance_test.go` 27, фейковый Executor). На живом стенде: `config/scenario.example.json` — ddmin 5 запусков, sequential 5, dependency_aware 5, принято [fault-1]; `config/scenarios/multi-fault-demo.json` — ddmin 9, sequential 10, dependency_aware 9, принято [fault-1], decoy отброшен; результат 3/3 ORIGINAL_FAILURE. Бюджет сценария `runs=3` и `seconds=4` дал `BUDGET_EXHAUSTED_RUNS` и `BUDGET_EXHAUSTED_SECONDS`. Это отдельные запуски, не серия повторов с доверительными интервалами; различие 9/10/9 запусков на одном сценарии не является выводом о преимуществе алгоритма.

Не выполнено: полный протокол из tests/EVALUATION.md (6 сценариев × 10 прогонов × оба алгоритма с Wilson CI) — это отдельная исследовательская задача с фиксацией характеристик машины, а не инженерная реализация; результаты туда не вписаны (tests/results.csv остаётся только с заголовком).
