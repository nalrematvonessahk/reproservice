## Замечания

1. **Подтверждено запуском. `sequential` отчитывается как `ddmin`.** `finish` в `src/reducer/ddmin.go:121` выбирает `algo` только по флагу `dependencyAware`, а `sequentialRemoval` всегда передаёт `false`. Пробный тест: запрошен `sequential`, в результате `Algorithm = "ddmin"`. API возвращает это поле (`src/controller/api.go`), UI показывает его. Если результаты эксперимента DEMO-50 группируются по этому полю, данные `sequential` попадут в группу `ddmin`. Исправление: передавать имя алгоритма в `finish`.
2. **Подтверждено запуском. Повторные запуски одних и тех же кандидатов, кэша нет.** Если сократить набор из 4 вмешательств, где нужны все 4, потребовалось 16 запусков; кандидаты `[a b]` и `[c d]` выполнены по два раза (подмножество, затем его дополнение при n=2). `docs/15-reducer-decision.md` обещает общий кэш для всех методов, в коде его нет. Повторы тратят бюджет и искажают `runs_used`, на сравнении которого построен исследовательский вопрос. Исправление: мемоизация по отсортированному набору ID внутри одного вызова `Reduce`, одинаково для всех алгоритмов.
3. **Не запускалось. Ноль платежей считается исходным нарушением.** `oracle.go:47` задаёт `Violated: count != 1`. Если запрос оформления заказа не дошёл до платежей (недоступен сервис, `http_error` до платежей), `count = 0`, `Violated = true`, и `executeOnce` возвращает `ORIGINAL_FAILURE`. Ветка `OTHER_FAILURE` (`orchestrator.go:142`) требует `!Violated`, поэтому для этого случая недостижима. Это ровно риск из `docs/09-team-plan.md`: «OTHER_FAILURE проходит как исходный». Для двойной оплаты достаточно `count > 1`; случай `count = 0` при ошибке checkout должен давать `OTHER_FAILURE`. Нужен интеграционный тест на этот случай.
4. **Не запускалось. Отмена не покрывает сокращение (FR09).** Сокращение выполняется синхронно внутри HTTP-запроса `reduceRun` и использует `r.Context()`. `Orchestrator.Cancel` ищет отмену только для основного запуска, и `cancelRun` (`api.go:146`) всё равно отвечает `cancel_requested`, не проверяя результат. Константа `StopCancelled` в `reducer.go:48` нигде не возвращается. Требование FR09: «Cancel прекращает новые кандидаты».
5. **Не запускалось. Хеш seed и дайджесты образов не проверяются (ADR-002).** `Runner.SeedHash` только пишется в лог при старте (`controller/main.go`); во всех примерах сценария `seed_hash = "TO_BE_COMPUTED"`, `image_digests = {}`. Повтор с другим окружением не блокируется, хотя в ADR-002 это требуется.
6. **Не запускалось. Тайм-аут checkout не останавливает запрос.** `runCheckoutWithTimeout` (`orchestrator.go:154`) возвращает ошибку через 15 с, но горутина с `sut.Checkout` продолжает работать, а контекст в неё не передаётся. Оракул может читать таблицу `payments`, пока запрос ещё что-то пишет. Исход `TIMEOUT` недостижим: тайм-аут становится `OTHER_FAILURE` (или `ORIGINAL_FAILURE` при замечании 3). В `src/controller/README.md` недостижимость `TIMEOUT` и `INAPPLICABLE` уже признана.
7. **Не запускалось. Сброс стенда.** `TRUNCATE` в `runner.go:56` без `RESTART IDENTITY`; после сброса проверяются только HTTP-проверки сервисов (`verifyHealth`), состояние БД и хеш seed не сверяются, хотя `docs/07-architecture.md` говорит «сверяются хеш seed и health checks».
8. **Не запускалось. Пагинация событий.** `api.go:125` превращает курсор в `time.UnixMilli`, а выборка использует `created_at > $2` с микросекундной точностью (`store.go`); последнее событие может вернуться повторно. Причину нужно подтвердить на стенде.
9. **Мелочи.** (а) В `finish` любая ошибка `confirm` превращается в `BUDGET_EXHAUSTED_RUNS`, даже если исчерпано время. (б) Неизвестный алгоритм даёт 500 `REDUCE_FAILED` вместо 400. (в) `reduceRun` не проверяет состояние исходного запуска. (г) Подтверждение 3/3 выполняется только для итогового набора; если в `docs/07-architecture.md` имелся в виду каждый принятый кандидат, это расхождение.
