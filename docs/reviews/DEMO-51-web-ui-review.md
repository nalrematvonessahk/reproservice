## Второй проход: замечания ultrareview к исправлениям выше

Облачный ultrareview ветки нашёл дефекты в самих исправлениях; все исправлены в следующем коммите и покрыты тестами `App.flow.test.tsx` / `api.test.ts` / `compare.test.ts`.

| № | Серьёзность | Суть | Исправление |
|---|---|---|---|
| 17 | M | Кнопка Reset в шапке оставалась активной во время сокращения: панель с «Cancel reduction» исчезала, отменить сокращение и загрузить сценарий было нельзя до конца бюджета | Reset, «Start a different run» и загрузка сценария заблокированы, пока что-то держит стенд (запуск, сокращение, сравнение) |
| 18 | M | После реплея запуска результат сокращения сбрасывался, а `mode="reduced"` в сравнении оставался: селектор показывал «None», а отправлялись все вмешательства | Режим откатывается на «none»; `reduced` без набора больше не превращается в «все» |
| 19 | L | Однородный результат повторов (все `PASS`, если исходный запуск не упал; все одинаковый `OTHER_FAILURE`) назывался «нестабильным» | Отдельный вердикт `uniform` |
| 20 | L | `waitForRun` (повторы сравнения) не переживал кратковременную ошибку, в отличие от основного опроса | Общая логика `isTransientError`/5 повторов |
| 21 | L | «Cancel comparison» между повторами ничего не делал, цикл продолжался | Флаг отмены: цикл останавливается, только что стартовавший запуск отменяется |
| 22 | L | «Cancel reduction» молча проглатывал ошибку и ответ `not_running` | Отдельный обработчик показывает ошибку или `CANCEL_NOT_APPLIED` |
| 23 | L | После 5 неудачных опросов опрос запуска прекращался навсегда, элементы, зависящие от `runActive`, оставались заблокированными | Опрос продолжается раз в 3 с и снимает ошибку при восстановлении (404 не повторяется) |
| 24 | L | Заметка о повторе ключа не учитывала другую версию сценария (тот же `id`) | Сравнивается и `version_id` |
| 25 | L | Единственный неудачный запрос финальной загрузки событий не повторялся, последние события терялись | До 5 повторов с нарастающей паузой |

 (не исправлялись, backend не менялся)

1. **Экспорт без конфигурации.** `docs/07-architecture.md` говорит только «GET /api/runs/{id}/export», FR12 — «JSON содержит schema_version, конфигурацию, outcome». Backend отдаёт `{schema_version, run, events}`. UI достраивает `scenario` и `reduction` на своей стороне; если нужен самодостаточный экспорт из API, это решение для автора backend.
2. **Тихое усечение экспорта на 10000 событиях** (`api.go`, `exportRun`). UI предупреждает при ровно 10000; признака усечения в ответе нет.
3. **`GET /api/runs/{id}/events` для несуществующего запуска → 200 `{"events":null}`**, а не 404 (`getRun`/`export` дают 404 `RUN_NOT_FOUND`).
4. **Курсор событий** — миллисекунды против микросекунд в БД: последнее событие приходит повторно (подтверждает DEMO-54, п. 8). UI теперь это переносит, причина осталась в backend.
5. **Идемпотентность и занятый стенд.** `createRun` вызывает `TryAcquire` до поиска по ключу, поэтому повтор того же ключа во время активного запуска получает **409 STAND_BUSY**, а не 200 с существующим запуском (проверено на стенде). `docs/07-architecture.md`: «повторный POST не создаёт второй run» — это верно, но ответ отличается от ожидаемого.
6. **Нет понятия «исправленная версия».** Backend знает версии *сценария*, а не сборки сервиса; «до/после» в UI — это разные наборы вмешательств при одном seed. Это записано в тексте панели и в ограничениях ниже.
7. **Окно между `COMPLETED` и освобождением стенда** (`runRegistered`: `SetOutcome`, затем `defer Release`): теоретически очередной запуск сразу после завершения может получить 409. В ручной проверке (6 запусков подряд) не воспроизведено; повторы сравнения повторяют запрос при `STAND_BUSY`.
