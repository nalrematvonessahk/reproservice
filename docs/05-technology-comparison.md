# Сравнение технологий и решения

Решения предварительные, их подтверждает руководитель и короткий технический пилот. Оценка качественная: производительность не измерялась. Источники T01–T08 и D04; выбор отражает требования проекта.

| Решение | Альтернатива 1 | Альтернатива 2 | Выбор и основание | Условие пересмотра |
|---|---|---|---|---|
| Прокси и контроллер | Go: HTTP-библиотека и конкурентные операции; команде нужен пилот | Python asyncio: быстрое прототипирование, знакомый стек; иной подход к конкурентности | Go для целевого MVP. В одном процессе удобно связать HTTP-перехват и планировщик; это инженерное решение, не доказательство большей скорости | Если технический пилот не даёт нужного контроля ответов, пересмотреть до интеграции |
| Метаданные | PostgreSQL: сервер, транзакции, несколько клиентов | SQLite: встроенная БД, простая локальная установка | PostgreSQL для метаданных; отдельная тестовая БД для SUT. Нужна изоляция данных экспериментов от состояния приложения | Если издержки установки мешают интервью-пилоту, рассмотреть SQLite для метаданных |
| Окружение | Docker Compose: один локальный многоконтейнерный стенд | Kubernetes: кластерная оркестрация, больше настройки | Docker Compose соответствует FR-01 и одному стенду. Kubernetes выходит за MVP | Только после работающего replay и реальной потребности пользователей |
| Интерфейс | React + TypeScript: компоненты и статическая типизация | Vue + TypeScript: альтернативная компонентная модель, опыт Тамерлана с Vue | React + TypeScript условно выбран для распределения работы; решение подтвердить с Askhat/Aldiyar | Если команда быстрее поддерживает Vue, смена до разработки интерфейса не меняет исследовательскую задачу |

## ADR 001 Управление на уровне HTTP

Контекст: требуется показать потерю ответа после успешной операции, сохранив наблюдаемость. Решение: прокси завершает запрос к upstream, записывает событие, затем применяет fault action к downstream. Последствие: тестируются прикладные HTTP-отказы; потоки ОС и внутренние таймеры не контролируются.

## ADR 002 Идентичность сценария

Сценарий хранит версию формата, digest контейнеров, seed данных, параметры тайм-аутов/повторов, селекторы событий, инвариант и бюджет. Ключ события строится из логической операции, сервиса, метода, пути и номера попытки. Случайный trace ID помогает связать трассу, но не является стабильным ключом replay. Если селектор не сопоставлен, результат INAPPLICABLE.

## ADR 003 Сокращение

Единица удаления — вмешательство, а не произвольный сетевой запрос. Кандидаты не меняют полезную нагрузку основного пользовательского действия. Перед каждой проверкой восстанавливаются данные. Отсутствие исходного нарушения, другая ошибка, тайм-аут и ошибка стенда различаются. Обычный ddmin и последовательное удаление являются baseline; приоритизация кандидатов по наблюдавшимся связям — экспериментальный вариант. Обязательная валидация одинакова. Уточнение: ADR-005.

## ADR 004 Хранение и доступ

Управляющий API слушает 127.0.0.1. Прокси и тестовые сервисы находятся в изолированной Compose-сети. Заголовки авторизации и cookie исключаются из журналов. Подключение произвольного Docker socket из веб-интерфейса запрещено; допускаются только заранее описанные стенды. Для первой версии доступны доверенные локальные пользователи, многопользовательский доступ не реализуется.
